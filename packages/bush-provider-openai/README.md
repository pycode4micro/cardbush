# Model failures and Responses compatibility

Responses, Chat Completions and Anthropic Messages normalize HTTP exceptions and streamed errors through `providerErrorPayload` / `providerFailureEvent`. They preserve the provider code (or typed error), status and request ID. Runtime's `modelFailurePolicy` owns the shared retry classification; adapters decode protocol-specific facts and never execute tools. See the [Runtime policy](../bush-runtime/README.md#model-failure-boundary).

The Responses adapter shares a compatibility profile through `ProviderCapabilityStore`, scoped to the endpoint configuration, credentials and model. Only an explicit rejection of a feature actually present on the wire selects this profile. Authentication, quota exhaustion, temporary service faults and unrelated input validation never change capabilities.

The compatible projection uses ordinary `mcp_search` / `mcp_call` function tools, sends full history with `store: false`, uses local input estimates, and sends tool images as attributed observations after their complete function-result batch. Progressive tool discovery, instructions, reasoning and tool results remain available. This remains a Responses API adapter; it does not switch API families or model settings.

An explicit feature rejection may retry with this projection before any text, reasoning, tool call or usage has been exposed. An early SSE rejection follows the same rule. Once output is exposed, the failure is returned and a confirmed capability observation can apply to subsequent requests. Cancellation and local validation/size failures never select the profile.

A missing or expired `previous_response_id` has a separate action: discard the stale anchor and send the complete local transcript, including completed tool results, without changing capabilities, schemas, cache routing or storage. The recovered response can anchor the next round. Auth errors, unrelated missing resources and failures after exposed output cannot enter this recovery.

Both actions consume the single wire-recovery allowance in Runtime's `ModelRequestAttempts`, shared across ordinary transport retries of the same round. A 503 after recovery reuses the recovered projection, even if a capability observation expires. It cannot reset the allowance or bring back the stale ID. Anthropic's explicit `cache_control` rejection uses the same allowance to remove that optional field. SDK automatic retries remain disabled.

An exact-count failure records the original error and returns no exact measurement, allowing Runtime to estimate locally. HTTP 404 / 405 / 501 mark only the counting route as unsupported; a counting failure never changes generation capabilities. Counting does not consume generation attempts.

`provider_compatibility` Runtime journal events retain the original code, message, HTTP status and provider request ID, plus whether recovery retried, succeeded, failed, or was deferred. Generation events include `providerAttempts` and `recoveryAttempts`; `provider_retry` uses the same counts. Diagnostic text redacts configured credentials. Console diagnostics carry request/session identifiers as well.

Profiles follow the capability-store expiry (7 days by default). Within that period, new conversations and app restarts reuse the endpoint-configuration/model profile immediately without another failed probe. Reusing a profile does not extend its expiry; new conversations after expiry evaluate the provider again. A successful compatible response also records the mode in its validated provider replay, so that existing conversation stays compatible after expiry/restart. Native historical calls are translated only in the outbound projection; persisted conversation data is never rewritten. The initial transition may invalidate a cache prefix once, after which the compatible history stays stable. Other models/endpoints retain their own profiles; changing endpoint configuration or credentials selects a separate profile.

Validation: `node --test packages/bush-provider-openai/test/*.test.mjs` after `npm run build:runtime`. `providerLoop.test.mjs` tests the same HTTP/streamed failures and completed-tool preservation across all three protocols. `responsesContinuation.test.mjs`, `providerCompatibility.test.mjs` and `protocolParity.test.mjs` cover bounded recovery, cancellation, chained faults, capability expiry and retained history.
