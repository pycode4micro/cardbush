# Computer Use 排查与对抗测试（2026-09-05）

本次检查 Windows Computer Use 插件、原生输入与展示层、会话并发及观察状态约束，并回归验证此前的终轮消息渲染修复。没有引入统一事实协议；插件继续通过标准 MCP 返回自己维护的结果。

## 发现与处理

| 问题 | 证据与修复 |
| --- | --- |
| 同一会话的并发请求误取消正在执行的操作 | 实际复现第二个请求被拒绝后，异常清理却结束了第一个请求。使用独立的忙碌错误类型，拒绝者不再释放持有者的展示/输入资源。 |
| 长文本在切窗后继续输入其他窗口 | 受控双窗口测试曾在错误窗口收到 856 个字符；初步修复在完整回归中仍出现过 1 个尾字符。改为逐 Unicode 码点发送，间隔 40ms，发送前后检查 HWND/PID/前台；原生钩子在失焦或暂停后拦截带本插件标记的按下事件，释放事件仍可完成。 |
| 同一进程的辅助窗口漏检 | 真实 WPF 双窗口复现。发现流程改为枚举可见顶层窗口，而非每个进程只取 MainWindowHandle。操作仍绑定观察时的准确窗口身份。 |
| 终端有真实文字变化，却被判定无进展 | 命令确已写出验证文件，前后截图也不同，但低分辨率全图平均差异未越过阈值。增加有界、非密码 UIA TextPattern 可见文本摘要用于进展判断，保留真正无变化时的停止保护。 |
| 目标截图失败后，桌面裁剪可能混入覆盖窗口 | 对原生 PrintWindow 返回失败进行故障注入。现在明确报错，不再将桌面裁剪冒充目标截图，也不签发相应观察状态。 |
| 新的失焦保护误伤主动最小化 | 补测最大化、最小化和恢复时复现调用被取消。仅在明确执行窗口操作期间允许其产生的前台变化；实际用户键鼠接管仍然有效。 |

另外补强了 UIA 执行前的进程/前台复核、拖拽路径检查、组合键异常时的释放，以及长输入与展示层空闲计时之间的协调。此前的后台观察 → 激活 → 再观察流程和预检失败预算修复一并保留。

## 复现入口

```powershell
npm run test --workspace=@cardbush/apps-mcp
npm run test:native --workspace=@cardbush/apps-mcp
```

原生测试需要交互式 Windows 桌面，终端测试需要 `wt.exe`。多个原生测试不要同时运行，否则会争用桌面。新测试报告位于 `%TEMP%/cardbush-computer-use-adversarial-*/report.json` 和 `%TEMP%/cardbush-terminal-fixture-*/report.json`；关联截图路径记录在报告中。

长输入切窗测试可单独运行：

```powershell
$env:CARDBUSH_TEST_FILTER='foreground changes'
$env:CARDBUSH_SWITCH_AFTER='3300'
node packages/cardbush-apps-mcp/test/computerUseAdversarial.native.mjs
Remove-Item Env:CARDBUSH_TEST_FILTER, Env:CARDBUSH_SWITCH_AFTER
```

会话 `local-f8490f55-d394-41a0-bbbb-03322618d28f` 的三张目标截图文件完全一致，不能据此声称命令已执行。受控终端测试证明：前台程序占用终端时，可以出现“输入已派发、画面没有变化、shell 命令没有执行”的现象。这与原记录相容，但没有当时的进程状态，不能将它当成历史原因的最终证明。

## 范围与限制

- 这是实际 Windows 桌面集成测试和工具边界对抗测试；没有覆盖所有第三方应用、UAC 安全桌面、远程桌面、多显示器/混合 DPI 组合，也没有开展模型层网页提示注入红队测试。
- Windows SendInput 仍是共享桌面机制，检查前台与系统派发之间不存在应用提供的原子隔离。这次重复测试未再观察到串窗，但不能承诺任意系统负载和调度下绝无竞态；不应把它当成操作系统安全隔离。
- 逐字符输入约为每秒 25 个码点，长文本比以前慢；长任务仍受调用方超时/取消约束。支持 UIA 的可写控件可以使用 `set_value`。
- 不支持 PrintWindow 的应用现在会明确报告目标截图失败；有界 UIA 文本摘要也不保证识别所有应用的全部微小变化。
- 测试通过不等于整个项目零 Bug。没有改动外部插件返回协议，没有提交或推送这些工作区修改。
