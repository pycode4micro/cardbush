- 工具层失败 4 次，全部是 `edit_file` 的 `edit_old_text_not_found`。
- 运行中权限请求 0 次，人工介入 0 次；评测开始前的发送目标授权不计作任务内介入。
- 每题的终端清理均未报告错误。

这些是 provider 返回的 token 用量，不是货币费用；终端命令返回非零退出码也不等于 Runtime 工具失败，当前原始报告没有单独统计前者。

## 两个失败样本

**FLAC 预览：** 两个 `edit_file` 在第 10 轮均找不到待替换文本，第 11 轮重新搜索后达到 token 阈值。两个目标源码文件相对于故障版均未改变；评分仍在 `isAudioPath('C:\\mix.FLAC')` 处得到 false。

**文件引用：** 第 10 轮 `edit_file` 找不到待替换文本，最终达到 token 阈值。目标源码未改变，`2026/9/29` 仍被拆成普通文本和 `/9/29` 本地链接。

本地 URL 任务也发生过一次相同编辑错误，但后来修复的源码通过了独立评分。这说明编辑失败后的恢复值得优先测量，单次错误并不必然导致最终修复失败。

运行结束后，8 个候选目录的 `test.mjs` 均能通过；其中失败的两题仍使用原始 smoke test，另有临时探针脚本，不能将这些脚本的成功退出算作完成回归验证。六个通过评分的任务修改了公开测试。独立评分器确实捕获了两个未修复故障。

## 固定条件与解释边界

- 接入目标：`https://api.deepseek.com`，使用用户明确授权的现有模型配置。
- Reasoning：high；每次响应最大输出 4,096 tokens；上下文窗口设为 100,000 tokens。
- 每题最多 24 次模型请求、300 秒；累计输入（含缓存）+ 输出达到 150,000 tokens 后，不再发起下一次模型请求。最后一次响应可越过阈值。
- 使用既定工具子集、`task_free` 和独立目录；不调用子 Agent。
- 每题只测一次，样本是受控注入故障，题目规模较小。

大量缓存输入仍计入这次累计 token 阈值，因此 37.5% 的正常收尾率依赖本轮预算设置。当前记录不足以把多余轮次归因于推理长度、重复验证或响应输出上限；下一轮需要补充每轮 finish reason、用量与终端退出码。

## 下一步建议

1. 优先复现并改善 `edit_old_text_not_found` 后的定位与恢复。记录失败时的目标位置和匹配信息，验证回读后重试；再用相同任务评估 patch 编辑是否改善成功率。
2. 分开评估源码修复与正常收尾，增加每轮记录，分别比较固定预算与调整后的输出上限，确定改善来自哪里。
3. 在这两个失败样本上建立受控对照后，再加入更大规模的跨文件任务与长会话恢复任务。
