# 优化后的按需压缩与提前工具摘要：实现和真实模型对照

本次在 `codex/final-reply-compaction` 分支优化旧方案并进行对照。评估阶段没有替用户选定默认方案；随后按用户明确选择，将提前工具摘要接入共用产品执行入口。没有部署服务、修改真实业务会话或运行业务工具。

主线安排：提前工具摘要方案并入 `main`，桌面、服务端 Agent 和 CLI 共用默认入口。切换前的主线版本（按需 checkpoint，包含本次 CLI 优化）保留在 `codex/checkpoint-compaction`，基点为 `24caf04`；本次改进后的 checkpoint 与旧摘要归并仍在新主线中作为兜底。该分支用于保留旧代码，不是新格式会话日志的自动降级通道。

结论：本次证据支持**优先采用提前工具摘要作为常规路径，优化后的按需 checkpoint 和旧摘要归并作为兜底**。旧方案的继承和范围处理已改善，后期单次输入更小；提前工具摘要仍保留信息更完整、累计请求更少。这是当前单场景连续样本的工程选择依据，不是对所有模型和任务的普遍证明。

## 实现

- 新增量压缩事务一次投递一个选中来源，附带此前已接受的摘要作为背景。保留真实当前用户消息作为历史与继续执行的分界，维护提示放在旧回执之后；来源编号不变，当前请求的消息范围重新映射。旧的未完成事务继续使用已保存的输入模式。
- 将历史 checkpoint 明确标记为继承的对话记忆，附上原始覆盖范围；不能把承载它的“收到、暂停”轮次当成全部内容。继承范围也包含之前被部分压缩的消息所属轮次。
- 超限时先按完整工具调用及全部回执分段，之后才考虑不可再分的大结果预览。正常长上下文对照的四次压缩均没有首尾预览裁切。不可分的超大调用仍可能需要归档预览或停止，不能承诺永远没有信息缩减。
- 所有历史来源已经是摘要、当前轮工作能保留时，按摘要实际覆盖的历史时间选最早约 **2/3 的序列化体积**，以完整来源为边界，至少保留一个近期来源。由模型合并成一个摘要，而不是静默丢弃旧摘要。它不是固定轮数或本地语义排名。
- 仅对这种全摘要归并提示模型以约 800–1,500 字符保留现行要求、关键状态和回看标记，避免完整重复历史解释。普通单来源摘要不采用这个短目标。模型自行决定内容，不通过本地语义匹配判定通过。
- 归并按继承历史的时间排序，不能按较新的 checkpoint 存放轮次排序。选中来源在原请求中不连续时，精确范围单独登记；中间未选中的近期消息不会被纳入摘要。分段及恢复保留这些间隔。
- 单段归并的原生工具调用已经包含完整摘要，提交后的回执使用 `summary_from_call` 引用该字段，不再重复保存正文。多来源和分段回执仍保留完整已接受摘要表；原生调用、推理与回放信息不被伪造或改写。
- 回执带 `conversation-history://turns/first/last` 标记。按需工具 `read_conversation_history` 从当前 Session 原日志读取用户更正、最终回复和工具记录，支持分页及版本校验，不导出隐藏推理/回放和图片载荷，不增加跨会话或文件系统访问权限。标记区间可能包含未选中的中间轮次，实际替换范围以 `source_ranges` 为准。
- 宿主仅验证来源、范围、引用和完整请求预算，不进行关键词、语义检索或“要求是否正确”的本地判定。不达理想目标时最多修订两次；之后若仍留有最低有效余量才接受，否则失败保留原文。理想目标是在触发线下保留最多 20%（上限 16k tokens），最低余量为其一半；接受时仍必须低于硬上限、低于传输预警、且输入量确实降低，事件记录 `admissionTargetInputTokens`。不会因超过理想目标几十 tokens 就把已有效压缩的请求判死。

模型、推理强度、最大输出沿用会话配置。没有动态修改顶层工具 schemas。原始 Session/Tool 日志不重写；归并、回执、覆盖关系均可恢复。

## 主对照条件

- 使用与上一轮相同的 normal 长场景：12 个业务轮次、14 条业务用户消息，其中包含两次轮内修改；同一会话连续四次压力压缩。另有每阶段的未压缩原文控制组。
- 内容包含开头句式和原句修改、短镜例外撤销、音效增益与花字绑定更正、素材授权到期、任务取消/失败/运行/完成、分版本验收、单次渲染授权与发布边界。
- `deepseek-flash` / Responses，推理 `max`，最大输出 128,000。配置总窗口 530,000；实验元数据将窗口缩至 168,000。主对照沿用上一轮受控 JSON/4 压力计数，包含内部重放对象，不能当作真实 tokenizer。它用于形成可重复压力条件，可能比实际适配器更早触发维护；报告中的输入输出 token 全部取服务端 usage。
- 旧组关闭提前摘要投影，新组开启。提前生成阶段使用各自固定工具定义，压力阶段双方目录相同；两组固定业务最终回复相同。模型收到真实工具校验错误后最多修正一次，两组一致计费；旧工具允许直接结束，不伪造工具回执。
- 每次压缩后才提出相同的 48 项盲测：16 项持续要求、20 项事实、12 项后续判断。标准答案隐藏，不把回答或评分写回上下文。
- 主对照最终完成 **67 次真实模型请求**。奇数阶段旧组先，偶数阶段新组先；不并发请求。每种方式只有一个连续长会话样本，192 个检查项不等于 192 个独立实验。
- 主对照完成后，补测发现并修复了全摘要归并的正文重复、历史时间排序，以及超过理想目标少量 tokens 即完全失败的问题。主对照四阶段未走全摘要归并，也都在理想目标以内提交，未使用新增的有限重试后最低余量准入；没有因主对照未胜出而重新选择更好的评分。

包括提前阶段、压力维护、普通确认回复、盲测；不含未压缩控制组。输出包括接口报告的推理及其他生成用量，不能当作用户可见回复长度。

## 缓存链与费用复核

2026-10-23 补充分析，仅读取已有记录，未再请求模型。逐请求验证 usage 完整且缓存输入不超过总输入，按请求 ID 去重。Responses 的 `input_tokens` 已包含缓存命中部分，`output_tokens` 已包含推理输出，均不能重复相加；这与 [DeepSeek Responses 用量定义](https://api-docs.deepseek.com/guides/responses_api/) 一致。命中率取总缓存输入 / 总输入，不平均各请求百分比。

主口径排除盲测及原文控制组，但保留提前摘要、维护、工具参数错误修正、普通继续回复的全部成本。模型是直连 DeepSeek 的 `deepseek-flash`。记录时间是北京时间周五 15:10–15:21；按核查当日 [官方人民币高峰价](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)：每百万缓存输入 0.04 元、非缓存输入 2 元、输出 8 元。这是公开价格估算，不是账户账单。

`费用 = (缓存输入 × 0.04 + 非缓存输入 × 2 + 输出 × 8) / 1,000,000`

| 指标，排除盲测 | 优化旧方案 | 提前摘要 |
| --- | ---: | ---: |
| 请求数 | 39 | 16 |
| 输入 tokens，含缓存 | 682,753 | 371,325 |
| 缓存命中输入 tokens | 363,391 | 240,640 |
| 缓存未命中输入 tokens | 319,362 | 130,685 |
| 加权输入命中率 | 53.22% | 64.81% |
| 输出 tokens，含推理 | 46,656 | 20,061 |
| 总 tokens，输入 + 输出 | 729,409 | 391,386 |
| 缓存输入费用 | 0.01453564 元 | 0.00962560 元 |
| 非缓存输入费用 | 0.63872400 元 | 0.26137000 元 |
| 输出费用 | 0.37324800 元 | 0.16048800 元 |

本样本新方案少 **46.34% 总 tokens**，命中率高 **11.58 个百分点**，费用低 **57.97%**。缓存输入、非缓存输入和输出三项用量均更少，在相同且非负的三类单价下不会因重新加权而反转。闲时单价全部减半，估算为 0.51325382 元与 0.21574180 元，比例不变。将记录用量假设为全未命中，费用为 1.738754 元与 0.903138 元；这只是价格敏感性计算，不是一次冷缓存实验。

若包含评分请求，旧方案是 801,831 总 tokens、56.09% 输入命中率、1.21427716 元；新方案是 453,273 总 tokens、68.86% 输入命中率、0.48799664 元。主结论不依赖把盲测费用计入。

### cache_chain 能证明和不能证明的内容

原探针保留了每个请求的可见消息、工具目录摘要和实际 usage，未保留完整 `cache_chain_observed` / `provider_input_observed` 事件。消息归档时还剔除了隐藏推理和 providerReplay，因此本次只能用 `CacheChainTracker` 离线检查**可见请求投影**，不能声称重建了原始 wire 缓存链。

排除盲测后的投影回放：旧方案 38 个可比较相邻请求中有 30 次前缀变化，新方案 15 个中有 12 次；两组参数变化均为 7 次，都是探针在准备阶段和压力阶段切换固定工具目录。压力阶段的工具目录 hash 两组相同、四阶段不变。这些前缀变化包含压缩、来源更换和不持久化的探针尾部指令，不能当成产品缺陷或缓存完全失效次数，也不支持宣称新方案缓存链从不打断。

实际计费以服务端 `cached_tokens` 为准：部分前缀仍可命中，甚至可复用更早请求建立的缓存。[官方缓存说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/) 也明确缓存是尽力而为，并非 100% 保证。每阶段的非盲测命中率为旧方案 74.93% / 54.17% / 46.75% / 44.30%，新方案 66.76% / 58.27% / 63.86% / 69.04%；不是每个阶段新方案都更高，累计费用四阶段均更低。

此前调试、盲测及原文控制组可能预热同一服务端缓存。**排除盲测费用不等于消除了它对缓存的影响。** 因此 57.97% 是这次记录的价格估算优势，不是独立冷缓存生产测量的长期保证。没有将共同的模拟业务执行或固定最终回复计入真实请求成本。

## 命中率原因追查与默认接入

用户确认采用新方案后，仅检查原日志和离线执行路径，没有重跑真实模型或调整对照探针。

- **排除两组请求并发的解释。** 原控制台记录有 67 次请求开始、67 次结束，最多同时在途 **1 次**，与探针逐个 `await` 的代码一致。两组 Session 轮流执行，并非同时调用模型。每组持有独立的 SessionStore 和 Runtime，缓存链观察状态没有混用。
- **Session ID 不会在本接入中切换 DeepSeek 缓存槽。** 适配器不会向 DeepSeek 发送 Session 派生的 `prompt_cache_key`。离线序列化确认：其他输入相同，仅更换 `sessionId`，发送的 Responses body 完全相同。这不能揭示服务端缓存调度，但没有本地按两个 Session 互相覆盖缓存的机制。[DeepSeek 文档](https://api-docs.deepseek.com/guides/responses_api/) 也明确此字段不受支持，缓存由服务端自动管理。
- **测试将新增执行记录集中放入摘要请求。** 新方案 130,685 个未命中输入中，114,299（87.46%）发生在 12 次摘要准备请求。模拟工具事实预先注入，没有真实任务中的中间模型调用；新内容在这一阶段首次出现，分母也少了反复读取同一前缀的正常执行请求。这是统计阶段的直接证据，不能把 114,299 全部精确归因于某一种服务端缓存失效。
- **8 次可见前缀变化来自测试专用尾部指令。** 新方案 12 次可见前缀变化中，有 8 次恰好从上一请求最后一条 developer 指令开始；该临时“只生成本轮摘要”的指令没有写入对话日志，下一轮会用记录的模型响应替代它。它不代表产品每轮重写历史。
- **另外 4 次来自实际压缩，7 次参数变化来自测试目录切换。** 四次压缩确实替换了历史工具交换，属于真实架构成本。准备阶段只提供最终回复工具，压力阶段提供固定的维护目录，导致 `tools` 参数七次来回变化；这两种目录都是测试设置，产品同一会话继续使用冻结目录。
- **新的摘要前缀可以再次命中。** 压缩后的四次盲测请求命中率分别为 92.47%、95.33%、96.13%、97.29%；证据表明摘要上下文本身可被缓存，不能推断任意正常任务都会达到这些比例。服务端缓存落盘为秒级，按已保存的前缀单元尽力命中，无法仅凭 usage 分离精确的落盘、淘汰和共享预热影响。
