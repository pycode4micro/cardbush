# 流式显示与历史对照

实验入口：`npm run preview:streaming-lab`。命令打印仅绑定本机的预览地址。
自动验证：`npm run test:streaming-lab`。

## 使用本机历史

`npm run preview:streaming-lab -- --history` 只读本机 runtime-state，默认取最近四个有完整快照的父任务 turn。
也可以加 `--session <sessionId>` 筛选任务，或重复 `--turn <turnId>` 精确选择记录。
`--runtime-root <目录>` 可指定另一份本地日志。没有原始事件的 turn 会明确报错。

已在运行的预览可以先执行 `node scripts/export-streaming-history.mjs --turn <turnId>`，
再刷新同一地址。`--build-only` 只构建预览文件，便于保留原来运行的服务和端口。
导出只包含回放所需的事件投影和工具结果，保存在 Git 忽略的 `tmp/streaming-lab/history.json`，
不把个人历史写入源码，也不会恢复 runtime 或执行任何历史工具。

页面可切换真实历史与模拟场景，显示来源任务、turn、原始时长、事件数量和记录缺口。
普通回放保留顺序和事件间隔，可选 1/4/16/64 倍速；“直接完成”逐个等待文字/工具边界落定后跳转，
用于查看结果。快速跳转、倍速回放的首字数字都不能作为原速性能结论。

`node scripts/test-streaming-history.mjs` 使用原始时间间隔和虚拟 16ms 帧验证历史，
结果在 `tmp/streaming-lab/history-results.json`。UI 测试发现该导出时会额外检查真实历史的
最终正文、子任务预览、引导，以及终轮之前不出现改动总结。

左侧保留原有 `createSegmentedAssistantStreamBuffers` 和 500ms 列表合批作为对照；
右侧使用正式的 `transcript/frameStreamBuffer`，增量到达后进入下一帧，默认每帧每条消息释放 24 个 Unicode 码点。
两侧复用真实 `ChatPanel`、消息投影、工具组件、改动总结和滚动控制。
输入是同一组本地事件，没有模型调用、真实工具执行或用户会话写入。

正式发送、控制操作（包括重新生成）和后台 turn 订阅统一使用逐帧队列。
`transcriptDelivery` 默认 `frame`：文字帧与协议段完成标记立即显示，纯工具状态继续 500ms 合批。
工具和引导先同步释放已有文字，再更新事实；Stop 和终轮同步排空队列。
中断后台订阅时保留协议段和事件 ID 检查点，续接后不会重复前缀或丢掉前一段。
非前缀快照通过专用正文替换函数处理，不伪造新 loop、不清空工具。

实验页、模拟场景和个人历史均不被主应用导入。旧队列只保留给对照和兼容导出。

## 已验证

- 段结束前，正式逐帧队列的文字已经进入实际可见的聊天区域。
- 已显示完的段收到 completion 时，仍提交空增量携带完成标记，保留归档规则。
- 同一消息的多个协议段、中文/emoji、突发增量不会重复或切断代理对。
- 工具边界同步释放已收到的文字，保留工具的 `contentOffset`，不等待动画。
- 引导封闭过程段，仍保持 turn 活跃；不显示终轮改动总结。
- 子任务、查看图像的执行预览在活动过程中独立显示。
- 正常完成和 Stop 保留改动总结；失败保留失败状态。
- 正常完成、引导、Stop、失败、长 Markdown 五组场景，在最终快照覆盖之前和重复快照合并之后，新旧消息与工具状态一致。
- 隐藏页面、终轮事件先于最后增量、重复事件、reset/dispose 和非前缀快照替换。
- 同一消息第二个协议段中断后续接、重复游标事件、修订前缀与按消息释放。
- 工具计数合批、媒体 DOM 稳定性、Stop/审批即时展示以及会话切换隔离。
- 长 Markdown 继续到达时，手动上滚保持阅读位置；回到底部按钮恢复跟随；切换主题保持历史位置。

测试输出保存在 `tmp/streaming-lab-ui-results.json`。页面的“首字释放”衡量的是进入消息状态的时间，
不是网络首 token 延迟；React Profiler 数字来自本地开发构建，不能当作生产性能基准。
“直接完成”用于边界和快照校验，不能用于比较真实流式速度。速度体验应使用“开始回放”。

## 本次历史对照

四个真实 turn 共 1,613 次文字增量、147 次工具运行，包含 CPI 走势图、带一个子任务的数据分析、
一次中途引导和一次 Stop。原始事件间隔下，消息正文、工具状态和位置在终轮后保持一致；
两个带完整快照的 turn 还核对了合并前状态以及历史最终回复正文。

消息状态的首次文字释放（虚拟时钟；不包含网络、React 和布局耗时）：

| 历史类型 | 原有路径 | 逐帧路径 |
| --- | ---: | ---: |
| CPI 走势图 | 277ms | 16ms |
| 数据分析 / 子任务 | 978ms | 16ms |
| 中途引导 | 3006ms | 16ms |
| Stop | 991ms | 16ms |

视频的引导和 Stop 记录没有完整消息快照，引导原文也缺失；仅回放留存的真实事件，
引导处显示明确的缺失占位。不能据此声称验证了这两段的完整历史加载。

实际组件测试还覆盖“一次性注入所有事件”的极端情况。旧路径延迟提交工具时，
工具所属消息可能在终轮之后才创建，造成归档 `status` 未收尾。
现在工具更新按事件顺序同步应用；终轮收尾归档副本，晚到工具的消息继承已结束 turn 的状态。
严格对照结果写入 `tmp/streaming-lab-burst-results.json`，不再把状态差异列为允许项。

## 验证范围

- 已覆盖三条 Hook 的接入约束、队列续接与快照修订、终轮/引导、真实历史和组件滚动回归。
- 回放不连接真实模型，性能数字不包含网络和生产构建的全部渲染开销。
- 超长 Markdown 的长期解析开销仍需持续观察，本次没有改写 Markdown 解析器。
- 真实历史回放聚焦文字/工具/引导/终轮，没有重建思考和计划 UI，也不执行历史 HTML/BI 生成。

逐帧输出现在是正式默认路径，对照页继续用于回归验证。
