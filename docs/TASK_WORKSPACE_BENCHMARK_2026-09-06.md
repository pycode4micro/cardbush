# 工作区规模与存储基准：2026-09-06

本轮补充测量 TaskWorkspaceManager 在真实 Git 仓库中的规模成本。测试使用合成文件和本地工作区管理器，不调用模型，不修改用户项目或生产数据。

## 方法

- Windows / Node 25.9.0；仓库与 Runtime 存储位于新建的系统临时目录，二者分开。每组结束后删除此组拥有的临时目录。
- 两组分别为 1,000 个生成文件 × 12 轮，以及 10,000 个生成文件 × 4 轮；另各有 `.gitignore` 和一个起始未跟踪文件。包含起始未提交修改。
- 文件一般为 2 KiB；每第 257 个文件为 128 KiB，每 10 个文件中有一个包含二进制内容。一个 1 MiB 的忽略文件应被排除。
- 每四轮依次执行：5 个文件产生新内容、恢复这 5 个文件的基线内容、产生另一版新内容、不修改文件。每轮测量开始、收尾和审查。
- 最后重新创建管理器读取持久化状态，重复审查三次，再应用到原项目、逆序撤回全部轮次并丢弃副本。
- 对创建、应用、撤回后的所有覆盖文件逐字节核对，并检查原项目 Git 索引没有被应用操作改变。检查无修改轮次、复用旧内容和重复审查的存储去重。
- 时长为墙钟时间；表中的开始、收尾和审查使用中位数。建仓库、写入测试修改、文件断言和存储清点不计入相应操作时长。没有清空操作系统缓存，样本量不足以代表其他机器的延迟分布。
- 空间使用 `stat.size` 累加，表示逻辑文件字节，包含内容 blob、清单和任务状态，不是文件系统实际分配空间。内存采样包含测试进程与夹具，不作为 Runtime 独立内存指标。
- 重新创建管理器只验证持久化状态的重新读取，本轮没有执行真实进程强杀或断电测试，也没有重跑模型能力基准。

## 结果

| 覆盖文件 / 轮次 | 创建副本 | 每轮开始 | 每轮收尾 | 审查当前工作区 |
| --- | ---: | ---: | ---: | ---: |
| 1,002 / 12 | 19.42 秒 | 1.09 秒 | 1.20 秒 | 1.28 秒 |
| 10,002 / 4 | 245.08 秒 | 9.02 秒 | 9.64 秒 | 8.77 秒 |

两组的全部字节断言通过，包含创建时的工作内容、修改后应用、全部轮次逆序撤回、原项目索引与源文件保护、重复读取，以及副本丢弃。没有发现新的恢复正确性错误。

10,002 文件组的无修改轮次，开始和收尾合计仍用了 18.48 秒。重新创建管理器后，三次重复审查分别为 9.47、31.02、11.12 秒；31.02 秒是观察到的最慢审查。这一组最终应用用时 11.62 秒，整段撤回用时 19.12 秒。

| 覆盖文件 | 每次新内容 | 每份全仓库清单 | 新内容版本数 | 丢弃副本后保留的历史逻辑大小 |
| --- | ---: | ---: | ---: | ---: |
| 1,002 | 10 KiB | 137,228 字节，约 134 KiB | 6 | 3.30 MiB |
| 10,002 | 10 KiB | 1,379,228 字节，约 1.32 MiB | 2 | 28.17 MiB |

无修改轮次、恢复已有版本及重复审查都没有新增 blob 或清单文件，轮次状态仍正常增长。内容去重符合预期，但清单增长受到全仓库大小影响；同样新增 10 KiB 内容，在 10,002 文件组中还需新增约 1.32 MiB 清单。

## 已定位的结构性成本

1. `TaskWorkspaceManager.#capture` 在每次开始、收尾和实时审查时枚举全体覆盖路径，串行读取并存储内容，再次枚举和逐文件复读校验。无修改轮次同样承担全仓库 I/O。
2. `review` 同时承担读取历史检查点和扫描当前目录。聊天历史与文件修改列表分别请求此接口，任务栏也请求它；同任务请求串行处理，重复的请求会再次扫描。加载历史因此依赖实时文件检查。
3. 内容 blob 按字节去重，但每个不同的快照都保存完整文件清单。只改 5 个文件时，元数据增长仍与仓库文件总数成正比。
4. 丢弃副本释放 checkout，历史 blob 和清单仍保留；目前没有历史回收策略。这是现有保留行为，不能根据本轮较短测试判断长期磁盘用量可控。

创建阶段还有逐个 blob 写入并同步落盘、串行复制文件的成本。本轮只测量创建总耗时，没有分别测定它们占用的时间，因此不能给各环节分配耗时比例。

下一步应先分离持久化检查点读取和实时工作区扫描，明确各调用方需要的数据；再优化捕获的 I/O 调度、首次持久化和清单复用。字节校验、冲突检查和中断恢复的语义应保持，文件时间和监听事件不能单独作为内容未变的证明。空间回收需要围绕仍被任务、检查点和未完成事务引用的数据设计，不应直接按文件年龄删除。

本轮规模测试可以收口，接下来围绕这些改动做同夹具的前后对比和相关正确性回归；已有通过的全量测试无需为增加轮次而重复执行。

## 复现

```powershell
npm run benchmark:task-workspaces -- --files 1000 --turns 12 --output tmp/workspace-benchmark/repeat-1000.json
npm run benchmark:task-workspaces -- --files 10000 --turns 4 --output tmp/workspace-benchmark/repeat-10000.json
```

入口：[benchmark-task-workspaces.mjs](../scripts/benchmark-task-workspaces.mjs)。[完整测量数据](TASK_WORKSPACE_BENCHMARK_2026-09-06.json)保留 Runtime 源码与构建产物的 SHA-256、逐次操作时间、每轮存储大小及逐项断言结果，两组使用相同 Runtime 实现。

首次 10,000 文件组在夹具 `git add` 阶段触发了脚本的 60 秒超时，尚未调用工作区管理器。随后将夹具 Git 命令的时限调整为 300 秒；生产 Runtime 的超时设置没有修改。
