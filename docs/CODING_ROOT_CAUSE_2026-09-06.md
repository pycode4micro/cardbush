# 编码可靠性：根因调查与修复（2026-09-06）

本轮先补齐诊断，再复现失败，最后修改工具结果的表示方式和两个确定的执行缺陷。原来的八题、故障源码快照、独立评分器、模型和默认预算保持相同。首次基线报告不覆盖。

## 已证实的故障

### 模型看到的源码表示与编辑器要求的原文之间存在转义负担

原实现把整个原始工具结果 `JSON.stringify` 成模型消息。源码成为 JSON 字符串中的内容，反斜杠和换行以转义形式出现在模型上下文中；大结果的 preview 又可能被嵌入一层 JSON。

诊断复跑 `run-bRAhfY` 中，FLAC 任务在第 9、10 轮重复提交同一错误：源码正则使用一个反斜杠，解析后的 `old_text` 使用两个。文件 SHA 与读取记录一致，完整读取仍在该次请求的上下文中，且没有被归档或截断。仅在诊断比较中将成对反斜杠缩减后，目标文本才与源码第 30 行精确一致。

这证明了该复现样本的匹配失败原因。第一次八题评测没有保存完整参数，不能倒推它的所有失败都完全相同。模型的新文本也包含多余反斜杠，因此自动宽松匹配旧文本会有把错误正则写进去的风险。

### 编辑工具把部分新源码当成替换指令

单处编辑原来调用 `String.replace(oldText, newText)`。JavaScript 会展开新文本中的 `$&`、`$'`、`$` 加反引号以及 `$$`，使实际写入内容偏离输入；replace-all 分支却是字面替换。已用离线失败测试复现，改为函数返回替换内容，统一字面写入语义。

### PowerShell 包装层在错误的作用域读取状态

诊断中出现了 `Get-ChildItem` 报错而工具返回 `exitCode: 0`。原包装层在 `& { command }` 之后读取 `$?`，得到的是脚本块调用的状态。现在在同一脚本块内、原命令之后立即读取状态，并用真实换行隔开包装代码，避免命令末尾注释吞掉后续逻辑。

测试覆盖末条命令失败、失败后显式恢复、末尾注释、终止性异常以及原有原生程序非零退出码。工具本身仍返回执行结果，命令退出码保持独立事实；没有根据 stderr 文本猜测成败。

## 结构上的改动

- `ToolRegistration.renderModelResult` 由工具定义可读文本，Runtime 核心负责保存、限额和传递。读取、搜索、终端输出和归档读取使用原文文本，元数据保留结构化表示。
- 原始 `result` 继续用于执行事实、UI、审查和回退。呈现函数收到副本；呈现出错时回退到原始 JSON，不更改工具执行状态。失败工具保留 Runtime 错误，不调用成功结果的呈现函数。
- 完整可读文本作为可选 `modelText` 随工具执行记录冻结并持久化。归档页码绑定这份原始表示，工具热更新、呈现函数变化或重启都不会重新排版已有归档。没有该字段的旧记录继续按原 JSON 读取。代价是本地执行记录会多保存一份文本。
- `edit_file` 的已观察版本、精确匹配和歧义检查仍有效。未引入自动反转义、模糊写入、任务特例或额外重试次数。

这轮没有增加另一套按行编辑 API。已观察到的问题先在表示边界解决；模型仍可能选错或记错旧文本，严格校验应继续拦住这种修改。

## 诊断与预算

每题保存完整工具记录、实际模型可见消息、任务源码版本、每次响应的结束原因和用量，以及独立的评测器停止原因。隐藏推理正文和 Provider 凭据不进入诊断报告。完整记录位于候选目录之外的 `runtime/diagnostic-trace.json`。

原实现诊断复跑中，FLAC 出现 3 次 `finishReason=length`，日期识别出现 1 次，输出都达到固定的 4,096 上限。评测器已支持单独设置 `--max-output-tokens`，默认仍为 4,096。

提高到 12,800 的两题对照都通过功能评分，且没有输出截断，但两题都因累计 token 阈值结束。因此增大输出上限没有单独解决收尾问题，也没有据此修改产品的完成判断或放宽默认评测预算。

累计阈值为每题 150,000 input（含缓存）+ output tokens，在下一次请求前检查，最后一次响应可以越过阈值。这是本次评测的停止规则，不是上下文窗口耗尽或货币费用。尚不能把预算中断统一归因于 Runtime 不会完成任务。

## 八题复测之后：取消事实修正与职责边界

验证目标、测试次数和收尾时机属于模型的决策。本地负责忠实传递文件内容与版本、工具参数、实际执行结果、退出码、用量和停止事实。不能因为看见测试输出或独立评分通过，就替模型宣告任务完成；也不能把评测器的预算中断归因为模型或 Provider 故障。

复查发现，评测器在下一轮输入计数前触发取消时，Runtime 的输入计数错误包装把取消误记为 `provider_input_token_count_failed`。离线测试复现了请求次数上限、累计 token 上限及计数期间取消三个路径的误报。现在统一按实际 Turn 取消信号记录 `status: stopped`；通用原因改为 `turn_stop_requested`，不假定取消一定来自用户。具体评测停止原因继续保存在独立的 `stopReason` 中，例如 `reported_token_threshold`。

输入计数接入与模型执行相同的有界取消等待，防止不响应取消的计数操作挂住 Turn；迟到的结果或异常不再生成第二个终止事实。没有 Turn 取消信号时，计数异常（包括 Provider 自己抛出的 `AbortError`）仍记录为真实 Provider 失败。

这项修改在 Runtime 构建和 43 项相关离线测试中通过。它发生在上述八题复测之后，没有新增真实模型调用；原始轨迹、JSON 汇总及 8/8 功能、5/8 正常收尾的历史测量保持原样。本轮没有增加验证或收尾策略。

## 八题复测之后：任务工作区

随后实现了独立 Git worktree、原始字节检查点和工作区级撤回，详见 [任务工作区说明](TASK_WORKSPACES.md)。新机制覆盖终端和脚本的文件改动，工具调用记录继续保存各自真实结果。计划未关闭时继续执行、空回复恢复等既有保障保留，模型仍决定具体工作与完成时机。

这项基础设施优化通过临时真实 Git 仓库、终端进程、故障恢复和界面测试验证，没有重跑付费模型；上述八题的数据和结论仍对应当时的实现。
