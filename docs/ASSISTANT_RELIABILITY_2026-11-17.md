# Assistant 状态与桌面控制改进

本轮延续实际微信文本、合成视频和 Windows 窗口激活测试。范围是运行时的执行事实、上下文工作集及桌面控制生命周期；模型选择工具、解释结果和决定后续动作的权责不变。

## 完成事件与回复

桥接终态和子任务终态可能属于同一个用户请求。现在使用宿主登记的 `responseTo` / `originMessageIds` 关联，不比较文本、不按时间窗口合并、不判断回复是否“多余”。

- 同一请求的新事实到达时，使尚未发布的模型草稿失效。模型重新取得包含新事实的上下文；取消后晚到的旧输出不能发布。
- 已派发的工具保持执行，其结果先提交，再进入下一轮模型请求。完成事件不会取消工具或重放副作用。
- 已经发布的回复不撤回；其后真实状态变化仍允许新通知，即使两次回复文字相同。
- 不同请求、不同收件人的事实保持独立。任务结果租约随上下文提交确认，失败及停止释放未提交租约，重启保留已消费的任务版本。

## 空闲上下文维护

Assistant 增加独立于模型硬容量的工作集预算。估算历史达到 64k tokens 时，在空闲阶段调用模型生成检查点，以约 32k tokens 的近期历史作为保留区，并至少保留最后 8 个完整协议单元。逐批处理，工作集低于 64k 触发线后停止，避免每轮重写缓存前缀；不是要求每次准确压到 32k。小上下文模型按容量比例降低门槛。协议单元不能拆开工具调用与回执；单个完整单元已超出维护批次预算时，返回 `context_checkpoint_source_too_large` 并保留原文，不静默截断。

摘要由模型通过 `checkpoint_context` 提交；本地只检查协议、大小、源版本及取消状态。原始追加日志、用户消息 ID 和任务交付版本保留。新输入、停止、重置和关闭取消维护；晚到的结果不能覆盖新历史。失败保留原文并退避，不循环重试，也不改变前台执行结果。已有长历史首次请求尚未完成维护时仍可能较慢。

每批最多约 32k 估算源 tokens，逐批提交，以降低大历史触发单次模型超时的概率。预算测量实际序列化后的摘要输入，包括历史思考内容、JSON 转义、旧摘要及任务事实，而不是使用普通对话的 token 投影。`runtime.assistant_conversation` 的 `read` 结果提供 `contextMaintenance`：阶段、前后估算 tokens、检查点数、耗时和失败码。日志只记录维护失败码，不输出历史内容或凭据。估算 tokens 与服务商计费 tokens 不等同；后台摘要本身也消耗模型调用。

## Windows 控制生命周期

常驻控制宿主改为预编译 GUI 可执行文件。发布构建生成当前哈希对应的 DLL/EXE，退休旧生成物；原有 ASAR 解包及原生签名范围包含这些文件。正式安装缺少原生文件时明确失败，不在用户机器临时编译替代文件。开发环境仍按需编译。

实际输入工作进程先建立原生输入队列并回报就绪，宿主随后向准确 PID 请求前台资格委托。是否授权仍由 Windows 决定，不能保证任意后台进程激活任意窗口。

系统拒绝激活时，返回原始 `activation_failed` 和实际前台事实，提供原生“将窗口带到前台”入口。点击只尝试激活绑定窗口，不重放点击、键盘或剪贴板操作。入口绑定控制作用域、HWND、PID 和进程启动时间，30 秒失效；目标变化、停止和执行结束都会撤销。后续输入仍须通过正常观察、前台、遮挡和用户接管检查。

MCP 将真实会话/执行身份与 UI 语言传给桌面工具。只有宿主允许名单中的内置桌面服务，才能通过 `cardbush/control_lifecycle=turn` 登记执行租约；远端声明本身不能获得这个能力，插件子 Agent 的 MCP 分支也不继承该允许名单。执行成功、失败或停止时释放已登记的控制租约。清理捕获原连接及原身份，不向重连后的服务提交旧释放，也不影响其他任务。清理调用有 2 秒期限。

## 验证记录

- Assistant、任务交付、即时引导、压缩、MCP 和执行资源回归：236 项通过，包含不响应取消的清理适配器，以及 inspect 回执提交期间到达的团队完成事件。
- 两个真实 stdio MCP 子进程的 Agent 集成测试通过：身份隔离、工具命名、独立清理、授权和原生资源。
- Apps MCP 自动回归：79 项通过。
- 原生恢复入口：错误 PID、重复请求身份、跨作用域控制/释放拒绝、执行结束、下一轮获取、30 秒失效及无输入重放通过。
- Windows 原生对抗测试：22 项通过，包括前台切换期间输入中止，其他窗口收到字符数为 0。夹具从后台启动时，通过真实恢复入口先取得前台条件，没有放松生产输入检查。
- `test:ui-localization`、`test:app-views`、App/原生 TypeScript 检查及生产构建通过。

真实模型复测使用当前配置的 DeepSeek，对隔离的历史副本累计提交 7 次检查点（含格式/长度不合规后的重交，共 10 次请求），工作集从约 167,849 降至 61,671 估算 tokens；原始追加日志保留。每次请求实计约 40k–50k 输入 tokens，单次耗时约 41–68 秒。没有将测试副本覆盖回真实用户历史。实际 App 的后台维护也已提交检查点，重启后从已保存进度继续。诊断中前后 tokens 统一排除前台工具目录，避免把无关工具描述误算成历史增长。

这是上下文维护的实测，不是压缩后微信消息端到端耗时的对比。旧版请求的真实文本回复仍曾耗时约 162 秒；此前合成视频桥接发送约 1.46 秒，主要等待发生在模型处理环节。不要将工作集缩小比例直接当成响应时间提升比例。

这些结果不等于 Windows 所有应用、企业应用控制策略或微软商店签名认证均已验证。模型响应速度、网络波动和摘要的信息保留质量仍需持续测量。
