# 上下文预算与截断恢复审查

2026-09-11。延续[上下文与 Cache Chain 审查](./CACHE_CHAIN_ARCHITECTURE_AUDIT_2026-09-11.md)，落实用户确认的日常/维护预算分离、截断恢复和超限保护。验证使用本地模拟 Provider、真实 SDK 连接本地 HTTP 服务，以及已有会话的只读回放；没有调用付费模型 API，没有重启正在运行的 CardBush。

## 预算与触发点

统一使用以下量：

- `C`：配置的上下文窗口。
- `O`：配置的日常最大输出，保持原设置。
- `M = min(16,384, O)`：初始维护输出额度。
- `S = min(2,048, max(128, floor(0.01 × (C - O))))`：现有的有界安全余量。
- 日常输入额度 `U = C - O`。
- 压缩触发点 `T = max(0, min(floor(0.95 × U), U - M - S))`。

在 `C = 400,000`、`O = 128,000` 时：`U = 272,000`，`M = 16,384`，`S = 2,048`，**T = 253,568**。原约 141,952 的触发点为后续维护保留了另一份完整日常输出；如今只预留独立维护额度。相比仅按 95% 得到的 258,400，仍提前约 4,832 token，以容纳维护请求。

这不保证界面每次都恰好在该数值触发：界面累计用量与下一次完整输入不同，后者还包括工具 schema、维护指令等；本地估算也不等于服务端计数。`context_compaction_started` 保存实际触发原因、输入测量方式、触发值和各项额度。

普通请求维持 `O`，不会逐轮改变最大输出。维护请求先用 `M`；因输出截断重试时加倍，最多使用 `O`，每个维护作业的截断/格式错误共用三次生成机会。典型额度为 16,384 → 32,768 → 65,536；第三次仍截断就明确失败。传输错误沿用既有 Provider 重试策略。每次实际发送前重新检查完整请求能否放入窗口。精确计数已经涵盖完整请求，不再叠加本地估算余量。

工具返回进入下一次上下文的额度按已完成响应的真实输入/输出计算，预留下一次维护空间。原始工具结果继续由原执行记录保存，不因输入额度减少而改写。真实 usage 到来后替换旧估算，不继续用偏高估算压缩工具回执。

## 恢复与单一事实记录

| 情况 | 行为 |
| --- | --- |
| 普通输出截断 | 保留已生成的完整文本/思考，最多两次续跑；不执行截断响应中的工具调用，不续传未完成的原生响应 |
| 压缩输出截断 | 从冻结来源重新生成完整检查点；部分文本、思考及 JSON 不进入主对话；共用每作业三次失败额度 |
| 错误 JSON、缺失或混合检查点调用 | 与压缩截断共用重试额度，最多追加两条简短纠正信息，不重复插入来源正文 |
| 正常请求收到明确的上下文超限错误 | 即使低于本地估算阈值，也进入维护；每轮最多两次由 Provider 拒绝触发的恢复 |
| 维护请求超限 | 先使用已有工具记录的持久化回执；仍放不下时按完整来源分段，不重复发送原封不动的超限请求 |
| 分段汇总 | 只暂存真实 assistant 检查点调用及注明 `staged:true, applied:false` 的回执；最后合并成功才提交主检查点 |
| 分段失败、取消或无法再分 | 保留原始上下文和旧检查点，不提交半份摘要 |
| 重启恢复 | 从未变的来源重新生成维护内容，恢复失败次数和输出额度；可能重做摘要计算，不重放已完成的外部工具 |

分段保持每组 assistant、并行工具调用及全部工具回执完整，不切割工具 JSON、文本消息或不透明推理数据。来源索引来自冻结的原始消息范围；历史工具的回执标明真正所属轮次。重复工具调用 ID 会作为检查点格式错误拒绝，避免合并时破坏对话结构。

暂存的每次 Provider 原始事件通过 `model_maintenance_response` 进入执行日志，保留部分思考、原生 replay 和错误。它们是执行事实，不是另一份可替代原始会话的历史。主对话仍只引用最终真实检查点交互，活跃、提交和恢复投影一致。维护期间到达的用户引导、应用上下文和异步结果延后追加，避免来源边界在中途变化。

输入超限只识别 Provider 的结构化错误代码和合适的状态码；授权、配额和一般 400 错误不会因文案提到 token 而变成压缩重试。计数接口明确拒绝超限时，同样保留真实错误再恢复，不伪造一个精确 token 数。最终对抗测试还证明：适配器把明确超限错误标为 `retryable: true` 时，旧分支会落入无限传输重试；已封住这一入口，超限恢复耗尽后直接保留原错误结束。

## Cache Chain 影响

普通请求的最大输出和历史前缀保持稳定。维护第一次在既有历史末尾追加固定来源索引和压力通知；后续纠正消息继续追加。维护改变输出额度时，输入计数校准可以复用已核对的相同输入前缀，实际请求参数变化仍被完整记录，不能为了“命中”掩盖断点。

真正提交检查点、维护分段、工具结果改成持久化回执都会改变请求输入，仍作为真实结构变化记录。分段是无法直接放入窗口时的应急路径，可能增加请求次数和冷输入。服务端缓存效果还取决于实际模型、路由和保留时间，离线验证不能证明线上命中率提高到某个值。

## 限制与下一步

维护分段最多 64 个节点。不可分割的超大消息/工具交换、仍然过大的合并结果会明确失败，要求缩小输入；不会静默丢弃开头记录。失败或重启后保留来源，不承诺从已经完成的中间摘要零成本续接。

如果供应商静默裁剪输入而不返回标记，Runtime 不能仅凭成功响应确认服务端是否丢弃内容。本地预检和原始日志保留来源，但不等于证明服务端未裁剪；这仍需要适配器协议能力和真实 API 验证，不通过猜测答复文案判断。

16,384 是统一的维护初始额度，不按模型名字或任务语义分类。它与有界加倍策略的摘要质量、实际失败率和请求成本仍需要小规模真实 API 验证，尤其是大量长轮、图片和长推理场景。默认策略保留可调实现入口，但本轮没有再增加用户必须配置的开关。

本次实现保留现有事实层和核心 loop，不需要再引入第二套历史或提示词分类器。下一步应固定样本和模型参数做受控 API 对照，比较总输入、未缓存输入、压缩次数、恢复成功率和摘要保真度；无需继续凭离线缓存数字扩大改造。
