# 工作簿的设计判断

用于新建工作簿、报告和视觉改稿。专业的表格首先方便读取、比较、输入和核对；美观来自清楚的组织与节制的格式，不是把每张表做成同一种仪表盘。用户模板、既有模型约定和打印要求优先。

## 让用途决定结构

原始数据适合连续、可筛选的表头与记录，避免合并数据区域影响排序和分析。计算模型应让输入、计算和结果的关系容易追踪；是否分表由规模与使用方式决定。报告需要突出结论、单位、口径与支持数据；仪表盘仅在概览确实有帮助时使用。简单清单不需要额外封面或多个装饰工作表。

借鉴用户参考中的疏密、强调方式和信息关系，保留指定名称、区域及公式。不要根据题目关键词自动套用深色表头、彩色卡片或统一宽度的列。

## 建立清楚而克制的层级

用字体、间距、对齐、数字格式和少量强调建立主次。颜色应表达类别、状态或重点；输入和公式的配色约定仅在适合当前模型或用户要求时采用，不强加为所有表格的规则。

列宽和行高随实际内容调整，避免标题被截断或数据区域被过大留白撑散。数值便于纵向比较，文字与数值按阅读需要对齐；单位与小数位保持一致。金额、日期和百分比保持真实类型，使用格式控制显示，不为美观改成字符串。零、缺失值和错误具有不同含义。

边框、底色和斑马纹用于帮助跟踪行列，不需要每个单元格都有粗边框。强调关键总计和异常，而非让所有单元格都争夺注意力。展示型报告可隐藏网格线；数据录入表是否保留网格线按用途决定。合并单元格可用于报告标题，不用于可筛选记录区。

## 视觉表达与能力边界

有数据关系才使用图表，保留来源、分类顺序、单位和可追溯的数据区域。不要为了让工作簿显得丰富而增加无用图表、图标或工作表。

当前 tools.ExcelJS 提供单元格、公式、格式、表对象、条件格式、图片及页面设置，但没有原生图表制作接口。需要可编辑图表时可用已有图表模板的 OOXML 定点编辑，或当前环境中已经验证的其他制作能力；图片图表不等同于可编辑图表。包含图表和复杂对象的现有文件不要未经验证就经 ExcelJS 整本重写，避免丢失未知部件。

## 查看实际工作簿

先设计并查看有代表性的真实数据区域或报告页，再将适合的样式应用到其余部分；不必为简单修改增加样稿步骤或确认流程。检查长文本、负数、较大值、空值和总计，防止样例数据好看而实际内容不可读。

CardBush 桌面版可预览 XLSX，无需 LibreOffice。有可用的原生界面观察工具时，打开会话中的实际 XLSX 文件链接或文件面板中的预览，再观察加载结果并查看目标工作表。远端文件需先通过现有文件传输能力成为桌面可读取的文件。不能把提取数据或格式代码当作视觉验收。

当前 Browser Use 的集成浏览器导航只接受 HTTP(S)，不能直接打开内部 cardbush-file 协议。内置预览存在，不等于文档 MCP 自带截图能力；没有原生界面观察工具时，可在转换引擎可用的情况下走 PDF 与 PDF 插件渲染路径，否则如实报告未进行视觉复核。

内置预览用于阅读检查，不保证公式已重算或复杂 Excel 功能与原生应用一致。打印或 PDF 交付还需检查页面宽度、缩放、重复表头、分页和裁切；交互型工作簿则重点检查筛选、冻结区域与滚动后的可读性。发现问题后调整并重新查看，报告实际完成的结构、计算、业务和视觉检查。
