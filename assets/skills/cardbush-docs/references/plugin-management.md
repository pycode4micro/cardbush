# CardBush 插件管理

界面入口为「应用中心 → 插件」，也可以固定到底部快捷区；`@插件` 只引用插件管理应用，继续按用户要求使用现有管理工具。

按用户要求处理 CardBush 插件。先读取 [CardBush 插件契约](plugin-contract.md)，按当前任务选择创建、安装或卸载流程。

## 宿主与边界

- 按安装对象选择流程。同一任务可以同时包含外部软件的插件、MCP 服务程序和 CardBush 的连接配置；本 skill 只覆盖其中的 CardBush 插件包部分。
- 将第三方 MCP 接入 CardBush 时，搜索并读取 [MCP 接入](mcp-management.md)。可直接注册 MCP 连接，无需额外创建 CardBush 插件包。外部软件的插件步骤不适用本 skill，不影响继续完成 CardBush 端接入。
- 新包采用根目录 `plugin.json` 的 Agent Plugins 标准，OpenAI 扩展放在 `extensions.com.openai`；旧 `.codex-plugin/plugin.json` 和 Claude 清单保留兼容读取。插件仍安装到 CardBush，由 CardBush 管理目录、配置和生命周期。
- 不为本任务调用 Codex 插件安装/卸载工具、运行 `codex plugin`，或改写 `.codex` 的插件缓存和市场配置。用户明确要求其他宿主时，该任务不适用本 skill。
- 插件拥有自己的 skill、MCP 或 app 组件及原生返回结果。不要为安装插件新增统一事实协议或改造 Runtime Built-in Tools。
- 配置已安装插件的 MCP 服务时，使用 [MCP 接入](mcp-management.md) 中的插件连接管理工具。`list_plugin_connections` 提供别名与版本，`configure_plugin_connection` 修改用户配置，`request_plugin_credentials` 私密录入客户端凭据；这些操作不需要修改插件包。
- 先区分用户要创建插件包、安装已有插件、停用还是卸载。已有明确请求即可按其范围执行，不增加重复确认。

## 创建

1. 在用户指定的工作目录创建插件包；使用契约中的最小清单，建议按 `name` 命名新包。导入已有文件夹或 ZIP 时名称可以带版本号，安装器以清单 `name` 确定身份。图标和声明的组件路径必须实际存在且位于包内。
2. 根据需要添加固定目录 `skills/` 和标准 `mcp.json`；只有 skill 的插件不需要 MCP。需要 Hooks 时按契约声明当前已支持的事件和处理器。OpenAI 注册的 `apps` 可使用 CardBush 的实验性 OpenAI 账户连接，实际可用性取决于账户授权与工具发现。不把 Claude 的专属组件作为新包标准。
3. 用 CardBush 实际清单加载器校验组件及路径。创建完成不等于已经安装，清单中出现 MCP 名称也不等于工具已连接。

### 打包时交接环境要求

有外部依赖的插件，在已有 Skill 或按需引用的安装说明中交代运行时版本范围、依赖清单或锁文件、启动方式、配置变量名称及获得方式、验证入口。原生库、GPU、桌面或其他服务只有相关功能确实需要时才说明；不将某台开发机的状态当成所有机器的前提。

保留目标 Agent 判断安装方式的空间：可给经过验证的示例，并注明其系统、账号和验证范围，不要求固定版本路径或一套通用安装脚本。包中保留可维护的源码、依赖声明和必要资源；不打包开发机虚拟环境、运行缓存、私有 `.env`、令牌或浏览器资料。启动路径优先使用包内相对位置及宿主提供的插件目录变量，避免写死开发机用户名和绝对解释器路径。

## 安装与更新

1. 从 CardBush 插件目录/配置确认准确 ID、来源、当前版本和状态。个人包可能覆盖同 ID 的内置包；更新前检查现有包内容，保留用户修改。
2. 已在公共目录中的插件，通过 CardBush 管理界面安装并启用。新的本地包通过“添加 → 从本地安装插件”选择完整包目录，使用宿主的本地安装流程。
3. 复制包后重新读取安装状态。此前卸载过的同 ID 插件可能仍为 `installed=false`，不能仅凭复制成功宣布重新启用。
4. 读取安装后的清单、安装/启用状态和实际 skill/MCP 发现结果；宿主自动发现目录变更。插件版本或包内服务代码变化会让该插件的本地 MCP 重连，不要求重启 CardBush；文档、图标或缓存变化不重启服务。遇到正在运行的 Turn，排队的更新在任务结束后自动应用；报告待生效并结束本轮，随后验证实际发现结果，不在同一活动轮内反复等待或中断用户当前工作。
5. 包中含 Hook 时，检查其定义是否已经在插件详情中由用户审核并信任。安装/启用与 Hook 信任分别生效；定义变更后旧信任失效，未审核的 Hook 保持跳过。报告实际状态，不代写信任配置。

发布更新时先核对目标环境能否满足新依赖，再激活新服务；环境尚未准备好时说明“包已安装，服务待配置”。单独修改包外的 Python/Node 安装依赖不在包目录监听范围内：使用 [MCP 接入](mcp-management.md) 的 `reconnect_mcp_server` 重连目标服务，或在“插件 → 服务与工具”使用“重新连接”。`mcp_search action=load` 只加载当前目录的工具定义，不会重启服务。技能文件能读到新说明不等于运行中的 MCP 已更新。

### 接收端根据实际环境配置

用户要求在当前 Agent 使用或修复刚收到的插件时，读取该包的 Skill、依赖声明和实际连接错误，再决定需要做什么。文件同步只安装包和启用状态，保留目标端连接参数；宿主不搬运本机环境，也不推断解释器、安装依赖或自动修正启动命令。插件自己的启动脚本仍按包声明运行。已有可用环境就复用，不因收到新包而重装。

- 以运行 MCP 的主机和账号为准核对系统、架构、Shell、工作目录、运行时与可写目录。独立 Agent 中 `local` 指 Agent 所在主机，服务账号的 PATH、用户目录和桌面会话可能不同于 SSH 登录账号。缺少一次连接不能证明整台机器没有能力。
- 按包声明选择目标端可用的解释器和安装方式，优先使用现有独立环境及锁文件。只处理当前功能的真实缺项，保留资源保护与并发限制；不要复制源机虚拟环境或批量改写其他插件。无法取得依赖时报告具体失败，不原样循环安装或重提业务任务。
- 配置名称和值应对应目标环境。使用宿主支持的连接设置或插件约定的私有配置位置，保留已有参数与权限；缺少凭据时使用可用的私密配置入口。不要从打包机器自动收集环境变量、密钥或登录态，也不要把值写入 Skill、聊天或普通日志。
- 验证覆盖当前用途：解释器和模块能加载、MCP 实际握手并发现预期工具；若任务需要 GPU，再核对对应原生库和进程可见性。“能识别显卡”“能编码视频”并不证明其他 GPU 功能已可用。默认做不调用模型、不提交业务任务的检查；范围不足就说明未验证的部分。

把已经配置的位置、适用环境和剩余缺项简短交接给后续任务，已有配置不必重复执行。Skill 是目标 Agent 的按需指导，复制文件不会自动发起模型任务，也不需要新增 Hooks 或宿主安装器。

## 停用与卸载

- 停用：保持 `installed=true`，设置 `enabled=false`。
- 卸载：使用 CardBush 插件页的卸载入口，先停止插件服务，再移除个人安装目录、插件专属数据、配置及凭据；共享账户与独立 MCP 保留。内置组件只能停用。
- 活动任务阻止卸载时，保留待移除状态并在任务结束后重试。不能仅将 installed/enabled 改为 false 冒充文件移除。
- 当前版本若未暴露可调用的卸载入口，如实说明缺口；在代码开发任务中复用现有 Product Host 实现补接入口。不要伪造成功、将停用冒充卸载，或绕过宿主直接热改配置文件。

## 完成标准

报告准确插件 ID、包位置、安装/启用状态以及已验证的组件。将“包已生成”“包已安装”“组件已可用”分别按证据说明。仅写好 skill 不会自动赋予模型新的插件管理工具。
